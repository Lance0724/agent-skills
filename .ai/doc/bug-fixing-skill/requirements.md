# 缺陷修复技能需求文档

## 概述

创建 `bug-fixing` Agent Skill，为已有行为异常提供“评估、修复、验证”的证据驱动流程。技能借鉴 Spec Kit Bug Fixing，并沿用 `new-feature` 的中文文档、阶段门槛、模板和评估用例组织方式。

- 文档模式：标准模式
- 目标用户：需要诊断和修复现有软件缺陷的开发者与编码代理
- 预期价值：把症状、根因、修复范围和验证证据串联起来，避免未经诊断的试错式修复和验证过度声明

## 目标

- 明确区分缺陷评估、源代码修复和修复验证三个阶段。
- 使每个缺陷都能从原始报告追踪到根因、变更和最终验证结果。
- 限制修复范围，要求对偏离既定诊断的变更显式记录。
- 使用真实复现场景和相关测试证明修复结果。

## 范围

### 包含

- 新增 `bug-fixing/SKILL.md`。
- 新增评估、修复记录和测试报告模板。
- 新增输出质量和触发边界评估用例。
- 产物写入 `.ai/doc/bugs/[bug-name]/assessment.md`、`fix.md`、`test.md`。

### 不包含

- 不实现 Spec Kit CLI 命令或安装 Spec Kit 扩展。
- 不把新增功能、需求设计或想法评估纳入缺陷修复流程。
- 不规定具体编程语言、测试框架或部署平台。

## 需求

### REQ-001：准确触发与边界

技能应在用户报告崩溃、回归、错误结果或其他已有行为异常并要求诊断或修复时触发；纯新增功能、一般代码审查和想法评估不得触发。

### REQ-002：三阶段流程

技能必须按“评估、修复、验证”推进，并为每个阶段定义前置条件、允许的写入范围和完成条件。

### REQ-003：证据化评估

评估阶段必须调查仓库、记录实际与预期行为、复现信息、受影响路径、根因证据和置信度，并给出 `confirmed`、`likely`、`not-a-bug` 或 `needs-evidence` 结论；该阶段不得修改源代码。

### REQ-004：受控修复

修复阶段只有在诊断足以支持修复时才能修改源代码。修改应解决根因、保持最小范围，并在 `fix.md` 中记录变更和任何范围偏离。

### REQ-005：独立验证

验证阶段不得为了通过检查而修改源代码。必须运行原始复现或等价行为路径，并记录测试及回归检查，最终给出 `verified`、`partial` 或 `failed`；未运行复现不得判定为 `verified`。

### REQ-006：中文与格式规范

技能、模板及其生成产物的自然语言内容使用中文；代码标识符、命令、路径和协议字段遵循项目约定。技能必须符合 Agent Skills 规范。

### REQ-007：评估覆盖

技能应提供至少三个输出质量场景和包含正负样例的触发评估，覆盖成功修复、证据不足和非缺陷边界。

## 用户故事

- 作为开发者，我希望先获得有证据的根因判断，再实施受控修复，以便避免修错问题或扩大变更范围。
- 作为审查者，我希望看到复现、变更和验证之间的追踪关系，以便判断缺陷是否真正解决。

## 验收标准

- [ ] AC-001：给定一个现有行为异常报告，技能能够创建独立的缺陷目录并生成三个阶段产物。
- [ ] AC-002：评估阶段没有源代码修改，并且根因结论包含仓库证据和置信度。
- [ ] AC-003：修复阶段仅修改评估范围内的文件；范围扩展时在 `fix.md` 中记录理由。
- [ ] AC-004：验证阶段实际执行原始复现或等价路径；未执行时结果只能是 `partial` 或 `failed`。
- [ ] AC-005：当报告属于预期行为或需求变更时，技能停止修复并明确输出 `not-a-bug`。
- [ ] AC-006：官方 `skills-ref` 验证通过，评估 JSON 文件语法有效。

## 约束与依赖

- 参考 Spec Kit Bug Fixing 的 `assess → fix → test` 语义，但使用本仓库的 `.ai/doc/` 路径和中文模板。
- 不覆盖已存在的缺陷产物；名称冲突时必须停止或选择新的唯一名称。
- 用户提供的错误现象视为有效事实；复现用于定位根因和形成验证基线，不用于质疑用户报告。
