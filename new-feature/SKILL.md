# 新功能开发工作流

此技能用于按“需求、规范、计划、执行”四个阶段交付新功能。四个阶段不得跳过；小型功能可以缩短文档，但仍须满足各阶段完成条件。

## 核心规则

1. `.ai/doc/[feature-name]/requirements.md`、`specification.md` 和 `TODO.md` 的自然语言内容必须使用中文；代码标识符、协议字段、命令和文件名遵循项目约定。
2. 新增代码注释必须使用中文；仅在解释设计意图、约束或非显而易见行为时添加注释。
3. 功能目录名必须使用英文 kebab-case，例如 `new-user-login`。
4. 先调查仓库中的现有代码、文档、测试和约定，再提出问题。仅询问仓库无法回答且会实质影响范围、行为或关键技术取舍的问题。
5. 使用 `REQ-`、`AC-`、`DES-`、`TASK-` 编号建立追踪关系。每条验收标准必须对应设计决策、实施任务和验证证据。
6. 进入下一阶段前，必须满足当前阶段的完成条件。

## 文档深度

在需求调查后选择文档深度。若不确定，使用标准模式。

### 轻量模式

仅当以下条件全部满足时使用：

- 变更局限于单一、边界清晰的模块。
- 不改变持久化数据结构、公共接口、权限或安全边界。
- 不涉及外部系统、迁移、兼容策略、独立发布操作或复杂回滚。
- 验收标准少且风险低，不存在影响设计的未决问题。

轻量模式仍须创建三个文档并保留追踪编号和阶段检查，但允许简写内容；不适用的章节填写“不适用”及原因，不得直接删除。

### 标准模式

任一轻量条件不满足时使用。完整填写三个模板，并覆盖接口、数据、兼容、迁移、回滚、风险和验证策略中所有适用内容。

## 流程概览

1. **需求**：调查现状，明确目标、范围、非目标、约束和验收标准，创建 `.ai/doc/[feature-name]/requirements.md`。
2. **规范**：基于需求和现有实现确定技术方案、影响范围及验证策略，创建 `.ai/doc/[feature-name]/specification.md`。
3. **计划**：将规范分解为可执行、可验证的任务，创建 `.ai/doc/[feature-name]/TODO.md`。
4. **执行**：按任务实施，运行真实变更路径并记录验证证据，持续更新 `TODO.md`。

## 第一步：需求

1. 调查相关代码、相似功能、项目文档、测试和既有约定。
2. 从用户请求和调查结果中提取已知信息，不重复询问仓库已经回答的问题。
3. 仅在存在实质性未决事项时询问用户；多个相关问题一次提出。
4. 确认功能名称并创建 `.ai/doc/[feature-name]/`。
5. 按 `references/requirements-template.md` 创建 `requirements.md`。

### 完成条件

- 目标、用户价值、范围和非目标明确。
- 每项需求和验收标准均有唯一编号，且验收标准可观察、可验证。
- 约束、依赖和边界条件已记录。
- 未决问题已解决，或明确标记为阻塞项；存在阻塞项时不得进入规范阶段。

## 第二步：规范

1. 读取 `requirements.md` 和所有受影响的现有实现。
2. 确定设计方案、受影响组件、接口或数据变化，以及适用的兼容、迁移和回滚策略。
3. 为设计决策分配 `DES-` 编号，并关联对应的 `REQ-` 和 `AC-`。
4. 为每条验收标准定义验证方式、执行命令或场景以及预期结果。
5. 按 `references/specification-template.md` 创建 `specification.md`。

### 完成条件

- 所有需求和验收标准均有对应设计。
- 关键技术取舍、边界条件和风险已有明确结论。
- 受影响模块、接口和数据变化可定位。
- 每条验收标准都有可执行的验证方案。
- 不存在阻塞实施的未决设计问题。

## 第三步：计划

1. 读取 `requirements.md` 和 `specification.md`。
2. 将设计拆分为小而完整的 `TASK-` 任务，标明关联需求、依赖、交付结果和验证方式。
3. 安排任务顺序；仅在功能确实需要发布操作时加入发布任务。
4. 按 `references/todo-template.md` 创建 `TODO.md`。

### 完成条件

- 所有设计决策和验收标准均被至少一个任务覆盖。
- 每个任务都有明确完成条件和验证方法。
- 依赖顺序可执行，不存在未说明的阻塞项。
- 发布任务仅在适用时存在。

## 第四步：执行

1. 编写任何代码前，读取 `requirements.md`、`specification.md` 和 `TODO.md`。
2. 开始任务前更新其状态；有依赖或修改范围重叠的任务必须串行，彼此独立且所有权明确的任务可以并行。
3. 按规范实施；若实现必须偏离规范，先更新相关文档和追踪关系。
4. 实施后运行真实变更路径。根据变更性质选择自动测试、冒烟验证或人工场景，不得以“测试未报错”替代行为验证。
5. 在 `TODO.md` 中记录实际命令或场景、观察结果和对应的 `AC-`，然后将任务标记为完成。

### 完成条件

- 所有任务均已完成，或明确标记为不适用并说明原因。
- 每条验收标准都有实际验证证据。
- 需求、规范、实现和任务状态保持一致。
- 适用的测试通过，真实变更路径已成功运行。
